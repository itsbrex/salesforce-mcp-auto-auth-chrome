Architecture review

salesforce-mcp-auto-auth-chrome

The package is small and mostly healthy — patch.py, utils.py, and instance.py are already deep modules: a simple interface hiding real work. The friction is concentrated in one place — the seam between the cookie orchestrator and the per-browser readers, which is held together by a stringly-typed family tag matched in three separate switch statements across two modules. Below are four deepening opportunities, ranked.

Candidates

1 · One seam per browser family

Strong stringly-typed dispatch

cookies.py · browsers.py · chromium.py · firefox.py · safari.py

Problem

The family string is matched in three switch statements across two modules: profile discovery in browsers.discover_sources, and both cookies._read_from_source and cookies._list_sids_from_source. Adding a browser family means editing three switches plus a reader module — the "what a family can do" knowledge is smeared across the codebase.

Solution

Give each family a reader adapter with one interface — discover(cfg), read(source, host, name), list_sids(source) — and attach it to the registry entry. The three switches collapse to one registry lookup; each reader becomes a deep module owning its family.

Before — dispatch smeared ×3

After — one adapter interface

Wins

  • Three switches → one lookup
  • Per-family knowledge in one place
  • New browser = one file, zero edits
  • Tests target interface, not internals
  • AI-navigable: family = module
  • Locality of dispatch restored
Deletion test — deleting the three switches forces the dispatch into one registry lookup: complexity concentrates, it doesn't just move. Strong signal.

2 · Split reading from resolution in cookies.py

Worth exploring god module

cookies.py → (readers) + orgs.py

Problem

cookies.py carries five unrelated responsibilities: read one sid, read a sid with source, discover orgs, resolve the session (with the subtle primary-vs-Lightning ranking heuristic), and parse env vars. Understanding "how is the org chosen" means wading past cookie plumbing; the ranking domain rule hides inside a loop.

Solution

Leave sid reading behind the reader seam (candidate 1) and lift org resolution — discover_orgs, resolve_session, and the primary/derived ranking — into an orgs.py module. Move parse_env to config/__main__ where its callers live.

Before — one module, five jobs

After — split by concern

Wins

  • Ranking rule gets a home + a name
  • Resolution testable without readers
  • Config parsing near its caller
  • Smaller modules, clearer intent

Pairs naturally with candidate 1 — do the seam first, then this split is mechanical.

3 · Shed the auth.py hop

Worth exploring shallow indirection

auth.py · patch.py

Problem

auth.py is a whole module that re-exports read_sid and wraps one deprecated shim already scheduled for removal. patch.py imports read_sid through it, so every call threads patch → auth → cookies for no leverage.

Solution

Point patch.py at cookies.read_sid directly and retire the shim on its announced schedule. The seam disappears; nothing is deepened because there was never any depth behind it.

Wins

  • One fewer module to trace
  • Import path matches reality
  • Deletes dead deprecation surface
  • No behaviour change
Note — read_sid_from_chrome is public API with a deprecation warning; honour the "next minor release" timeline before deleting. An ADR is only worth writing if you decide to keep the shim longer than announced.

4 · Fold the read_sid wrapper

Speculative shallow wrapper

cookies.py

Problem

read_sid is read_sid_with_source(...)[0] — a shallow module whose interface is nearly its whole implementation. Two names for one behaviour is a small navigation tax.

Solution

Make the sourced form the single public entry point and let the two patch.py call sites take .sid themselves — or keep read_sid as the only public one and inline the tuple form. Either way, one name.

Wins

  • One reading entry point
  • Slightly smaller interface

Lowest value — the wrapper does earn its keep as a readable call site in patch._fresh_sid. Only worth touching if candidate 1 is already reshaping this module.

Top recommendation

Strong 1 · One seam per browser family

This is the only place in the package where complexity is genuinely smeared rather than hidden. Collapsing the three family switches into one reader adapter interface turns three shallow dispatch points into three deep modules, restores locality (a browser family lives in exactly one file), and lets the tests exercise a real interface instead of monkeypatching reader function names onto the cookies namespace. Candidates 2–4 get easier once this seam exists, so start here.

Suggested order: 1 → 2 (mechanical after 1) → 3 (schedule-gated) → 4 (optional).
